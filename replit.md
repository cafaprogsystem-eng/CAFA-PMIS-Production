# CAFA PMIS

Project management information system for the CAFA Development Organization / منظمة كافا للتنمية (Sudan operations). Tracks projects, beneficiaries, budgets, reports, and risks across the 18-State Sudan master-data registry with multi-level approval workflows.

## Current release authority

This file is collaborator context, not a deployment or handoff authority. Use
`README.md` for clean-clone setup, `docs/github-handoff-closure.md` for the
single GitHub-handoff verdict, and `docs/aws-deployment-runbook.md` for the
AWS release/recovery model. Do not rely on older notes below for production

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (proxied at `/api`)
- `pnpm --filter @workspace/cafa-pmis run dev` — run the web app (proxied at `/`)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks + Zod schemas from `lib/api-spec/openapi.yaml`
- `pnpm run check:api-contract` — regenerate twice and fail if generated source or committed declarations drift
- `pnpm --filter @workspace/db run push-force:development` — local development schema utility only; never use for staging or production
- `pnpm --filter @workspace/db exec tsx src/seed.ts` — reseed demo data
- Required env: `DATABASE_URL`

### API contract guard

GitHub Actions runs `pnpm run check:api-contract` before the workspace
typecheck. If it reports drift, run
`pnpm --filter @workspace/api-spec run codegen` and commit the generated source
and declaration outputs; do not hand-edit those files.

## Architecture decisions

- **Auth**: username/email + password via `POST /api/auth/login` (bcryptjs) creates a random opaque `cafa_sid` token stored only as a hash in `auth_sessions` (8h, or 30d when "remember me" is set). HTTP and Socket.IO look up the active, unrevoked server session; numeric legacy user-ID cookies never authenticate. `POST /api/auth/logout` revokes the targeted session and clears the cookie. `requireAuth` gates non-public API routes. The `X-User-Id` role harness is available only when explicit non-production demo mode is enabled and the active session belongs to a super_admin; it is never a no-cookie fallback or production authority.
- **7 valid roles**: super_admin, executive_director, program_manager, senior_coordinator, technical_coordinator, state_manager, state_officer.
- **Sector taxonomy**: use the current canonical sector source modules and do not add page-local lists. The maintained release decision is the seven main-sector taxonomy with its shared aliases/sub-sectors and assistance modalities; consult the source/validation before changing labels or values.
- **Technical Coordinator scope**: `users.sector` may store a comma-separated canonical sector assignment. `attachCurrentUser` parses it into `req.currentUser.sectors`; `tcSectorRestriction` is fail-closed, so an unassigned/malformed TC receives an empty restriction rather than unrestricted access. The current dashboard/location scope must be inferred from the current endpoint policy and its tests, not the historical broad-scope claim previously recorded here.
- **Permission model**: dot-namespaced strings (`projects.create`, `reports.approve.final`, …) computed from the user's `role` by `permissionsFor()`. `*` grants all. UI gates with `hasPerm(perms, code)`; backend route-level enforcement is **not yet wired** for most modules — UI checks are advisory only for the MVP. **Exception**: the `/users` admin routes enforce `requireAdmin` (super_admin) for write ops and `requireAdminOrPM` for reads; `program_manager` gets `users.view` only.
- **Comments & Revisions**: per-entity threaded comments on `project`/`report`. Server enforces a role→type allow-list (e.g. only Program Manager / Senior Coordinator / Technical Coordinator may post `required_correction`); TC sector-guard applies to all comment reads/writes. Two transition gates wired in projects + reports: (1) `final_approve` is blocked when any open `required_correction` exists on the entity (error `unresolved_required_corrections` + count); (2) `request_revision`/`reject` require a non-empty `comment` (error `comment_required_for_revision_or_reject`) and auto-mirror the rationale into the comment thread (`revision_request` / `rejection_reason`). On every transition `notifyEntityActors()` fans out in-app notifications to the submitter and assignees.
- **Approval workflows**:
  - **Projects** — draft → submitted → technically_approved → coordination_approved → approved → active → closed. Chain: State Program Officer → Technical Coordinator → Senior Program Coordinator → Program Manager. The legacy `state_review` step has been removed; in-flight rows in `state_reviewed` were migrated to `submitted`.
  - **Reports** — draft → submitted → coordination_approved → approved (→ archived). Chain: SPO/TC creates → Senior Program Coordinator coordinates → Program Manager approves. State Office Manager is monitoring-only and not in either chain.
  - Backend state machines (`PROJECT_TRANSITIONS`, `REPORT_TRANSITIONS`) live alongside their routes and are mirrored in the UI pages.
- **Audit trail**: every mutating route calls `logAudit(...)` which writes to `audit_log` with before/after snapshots. Surfaced on the Audit Log page.
- **Dashboard aggregates**: computed live from SQL in `routes/dashboard.ts` — no precomputed materialized views.

## Product

CAFA PMIS gives Sudan-based humanitarian staff one place to:

- Track 12+ active projects across health, WASH, protection, livelihoods, education, and other sectors
- Monitor the 18-State Sudan registry and its localities, with per-state KPIs and beneficiary breakdowns
- Register beneficiaries by category (IDP, returnee, host community, refugee) with disability/gender breakdowns
- Plan and track budgets at project, output, and activity levels against donor allocations
- Submit and approve narrative reports (monthly/quarterly/annual/ad-hoc) through the 5-stage approval chain
- Log and triage operational/security/financial/programmatic/environmental risks on a severity × likelihood heatmap
- Audit every state change with full before/after diffs

Use the avatar in the header (top right) to switch between demo users (super admin, country director, state coordinator, M&E officer, etc.) and see how the UI changes per role.

## Gotchas

- Do **not** run `pnpm dev` or `pnpm run dev` at the workspace root — apps are launched by Replit workflows that inject `PORT` / `BASE_PATH`.
- After editing `lib/api-spec/openapi.yaml`, run `pnpm --filter @workspace/api-spec run codegen` before typechecking.
- The shared proxy is at `localhost:80`; use `localhost:80/api/...` for ad-hoc curl. Never hit service ports directly.
- Backend authz is enforced via `requirePerm(...)` on all write routes and the audit log. Dashboard routes are scoped by user role/state/sector. Read-only list routes (projects, reports, risks) are TC-sector-filtered server-side but not yet per-state restricted for state roles on list views — the `stateId` filter is applied on the dashboard and detail mutation guards.
- The login page (`pages/login.tsx`) is the only screen translated EN/AR (RTL-aware via `dir="rtl"`). Strings live in `lib/i18n.ts` (`LOGIN_STRINGS`); the language choice is stored in `localStorage["cafa.lang"]`. The rest of the app is English-only — full app i18n is deferred.
- Demo credentials for all seeded users: password `cafa2026`; usernames are email local-parts (e.g. `amira`, `fatima`, `ahmed.m`). Reset by re-running the seed.
- Report `kind` is a free-form string at the API; UI offers `monthly | quarterly | annual | adhoc`. Seeded data and OpenAPI description mention additional kinds (`activity`, `progress`, `donor`, …) — reconcile before locking the contract.
- Project lifecycle is workflow-driven (`status` = draft → submitted → … → approved). The spec's "Project Status" dropdown (Planning/Active/On Hold/Completed/Closed) is intentionally **not** added as a separate field — adding it would create two competing sources of truth. If a manual operational status is needed alongside the approval workflow, add it as a new column (e.g. `operational_status`) rather than overloading `status`.
- Activity-level `locality_id` and `responsible_user_id` are persisted but not yet exposed on `GET /projects/:id/activities`. Add to the read DTO when the detail UI needs to surface them.
- The legacy `beneficiaries` table + `/api/beneficiaries` routes are still present and used by some dashboard widgets / audit log joins. The new segregated counts (`projects.beneficiaries_{male,female,boys,girls}`) are the source of truth for the dashboard breakdown modal and are populated only from the project registration form. Existing seeded projects have zeros until re-saved.

## Deployment guide

AWS staging and production operations are defined exclusively in
[`docs/aws-deployment-runbook.md`](docs/aws-deployment-runbook.md), with
[`DEPLOYMENT.md`](DEPLOYMENT.md) as the concise operator entry point and
[`BACKUP_RESTORE.md`](BACKUP_RESTORE.md) as the recovery guide.

The deployment path is migration-first: an ECS one-shot task runs
`node --enable-source-maps /app/scripts/migrate.mjs` and must succeed before
the one-replica application service is updated. The service itself runs with
`RUN_MIGRATIONS_ON_STARTUP=false`; it verifies the tracked schema head before
serving readiness. Do not use development schema push commands, seed data, or
fixture provisioning in staging/production release procedures.

The environment-name template is [`.env.production.example`](.env.production.example).
Use names and placeholders only: production/staging secrets live in their
environment's managed secret store, never in this file or a committed `.env`.

The single staging infrastructure definition is
[`infra/aws-staging/template.yaml`](infra/aws-staging/template.yaml), operated
by [`infra/aws-staging/deploy-staging.sh`](infra/aws-staging/deploy-staging.sh).
It is migration-gated and fails closed when AWS identity, approved region,
certificate, hostname, or staging secret inputs are unavailable. It must never
be used with production resource names or credentials.
